# 🎟️ Промо-акция «Чек на удачу»

Веб-сервис для проведения маркетинговой промо-акции. Покупатели регистрируют кассовые чеки для участия в розыгрыше призов, а модераторы проверяют их корректность.

### Основной функционал:
* **Покупатель:**
  - Регистрация и авторизация
  - Быстрый ввод чека через авторазбор QR-кода или вручную
  - Двухуровневая валидация данных на клиенте и сервере
  - Личный кабинет со списком чеков, статусами проверки и причинами отклонения
* **Модератор:**
  - Проверка чеков в админ-панели со сменой статусов
  - Обязательное указание причины при отклонении
  - Экспорт реестра принятых чеков в CSV с поддержкой Excel
* **REST API:**
  - Защищенный эндпоинт `/api/receipts/` для получения списка чеков в формате JSON со строгой изоляцией данных

## 🚀 Быстрый запуск

1. Склонировать репозиторий и перейти в папку проекта:
```bash
git clone https://github.com/itskeimy/test_task_first.git
cd test_task_first
```

2. Подготовить файл окружения:
```bash
cp .env.example .env
```

3. Поднять сервисы:
```bash
docker compose up -d
```
> Миграции базы данных и сборка статики применяются автоматически на старте веб-контейнера.

4. Создать учетную запись модератора:
```bash
docker compose exec web python manage.py createsuperuser
```

Сервис готов к работе:
* **Главная страница:** http://localhost:8099
* **Админ-панель:** http://localhost:8099/admin
* **JSON API:** http://localhost:8099/api/receipts/

## 💡 Архитектурные особенности

* **Учет 11 часовых поясов РФ:**
  Кассовый чек по 54-ФЗ содержит только локальное время торговой точки без таймзоны и указания региона. Разница во времени между Калининградом и Камчаткой составляет 10 часов.
  
  Если проверять время строго по часам сервера в Москве, покупатель на Камчатке утром не смог бы зарегистрировать чек, так как в Москве еще ночь предыдущего дня. Также чек с Камчатки сервер ошибочно отклонил бы как чек из будущего.

  Решение проблемы:
  1. Попадание в период акции валидируется по календарному дню торговой точки: от даты старта до даты завершения включительно.
  2. Защита от чеков из будущего берет московское время сервера с запасом +9 часов (время самого восточного пояса страны, Камчатки).

  ```python
  # Защита от чеков из будущего с учетом времени Камчатки (+9 часов к МСК)
  max_allowed_time = now_msk + timedelta(hours=9)
  if purchase_date > max_allowed_time:
      raise forms.ValidationError("Дата покупки не может быть в будущем.")

  # Проверка периода акции по календарному дню торговой точки
  if not (promo_start.date() <= purchase_date.date() <= promo_end.date()):
      raise forms.ValidationError("Чек не входит в период проведения акции.")
  ```

* **Решение проблемы N+1:** В админ-панели чеков настроен `list_select_related`. Данные пользователей подтягиваются одним SQL-запросом через JOIN вместо сотен повторных обращений к базе.

* **Изоляция и кэширование в Nginx:** Статика отдается напрямую в обход Python. Для публичных страниц включен RAM-микрокэш, который автоматически отключается по кукам sessionid и csrftoken для полной изоляции приватных данных.

* **Защита от дубликатов по 54-ФЗ:** Тройка `ФН + ФД + ФП` уникальна на уровне базы данных. Форма перехватывает повторную регистрацию до записи в БД и отдает понятный HTTP 400 вместо падения сервера с 500 ошибкой. Отклоненные чеки блокируются от повторного ввода во избежание спама.

* **Финансовая точность через Decimal:** Суммы чеков хранятся и валидируются исключительно через Decimal в коде и числовой тип NUMERIC в базе данных. Тип float исключен для защиты от погрешностей округления с плавающей точкой и потери копеек.

## 📊 Нагрузочное тестирование (RPS)

Результаты реального замера через `ApacheBench`:

| Сценарий | RPS | Время ответа | Ошибки |
|---|---|---|---|
| **Страницы с микрокэшем Nginx** | **~2 000 req/s** | 61 мс | 0% |
| **Личный кабинет с запросом к PostgreSQL (без кэша)** | **~135 req/s** | 175 мс | 0% |

> Микрокэш в RAM (`/dev/shm`, TTL 2 сек) дает **15-кратный прирост RPS** для публичного трафика. При авторизации пользователя кэш автоматически выключается для строгой изоляции данных.

### Команды для запуска тестов:

```bash
# 1. Замер страниц с микрокэшем (5 000 запросов, 100 одновременных соединений)
ab -n 5000 -c 100 http://127.0.0.1:8099/

# 2. Замер личного кабинета с выборкой из PostgreSQL (с авторизационной кукой в обход кэша)
ab -n 1000 -c 20 -C "sessionid=<ВАШ_SESSION_ID>" http://127.0.0.1:8099/
```

## ⚙️ CI / CD

В проекте настроена автоматизация через GitHub Actions при пуше в основную ветку:

* **Проверка качества кода и тесты:**
  - Поднимается тестовая база данных PostgreSQL
  - Проверка стиля и форматирования через Ruff
  - Строгая проверка типов через Pyright
  - Запуск полного набора автотестов через Pytest

* **Сборка и публикация в GHCR:**
  - Сборка Docker-образа с кэшированием слоев в GitHub Actions
  - Публикация в GHCR

* **Автоматический деплой на сервер:**
  - Подключение к VPS по SSH
  - Бесшовное обновление контейнеров через Docker Compose

## 🤖 Работа с ИИ

* **Где помог больше всего:** перенос дизайна из Figma во фронтенд: точная сборка адаптивной сетки от 375px, верстка модальных окон и тултипов ошибок. Также нейросеть ускорила подготовку базового конфига Nginx под отдачу статики и Gunicorn.
* **Что выдал с ошибкой и как заметили:** в конфиге Nginx модель настроила сквозной микрокэш для всех GET-запросов без исключений. При авторизации это приводило к утечке приватных данных: личный кабинет первого вошедшего пользователя кэшировался и отдавался остальным. Ошибку выявили при ручной проверке авторизации в двух браузерах, после чего добавили директивы proxy_cache_bypass и proxy_no_cache по кукам sessionid и csrftoken.
* **Что переписал бы при наличии времени:** подключил бы Redis для кэширования повторных запросов к базе данных, внедрил бы сканирование QR-кода напрямую через камеру или фото со сжатием на клиенте через JS-библиотеку, а также расширил бы поля профиля пользователя и доработал визуал интерфейса.
